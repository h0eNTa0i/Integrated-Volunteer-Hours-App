## 📌 TL;DR（执行摘要）

- **核心目标**：打造一款面向中国大学生的「志愿时长认证与活动管理」轻量工具，以「报名→签到→时长→证明」30 秒闭环，解决志愿时长认定不透明、易漏记、证书不可验证的核心痛点。
- **关键决策**：定位为「校园志愿执行工具 + 官方平台上游数据生产方」，不做官方认证替代者；以「月活跃认证时长」为北极星指标，单点切入 2-3 所试点校自下而上渗透。
- **MVP 范围**：R1-R7 共 7 项（活动展示、报名+学籍档案、学号校验、GPS+二维码签到、双端签退计时、总时长统计、PDF 证书导出），约 46 人日（折算 60 人日），6-8 周交付。
- **差异化**：学籍字段精准闭环 + 定位/二维码双签到防作弊 + 一键 PDF 证书（唯一编号/二维码可在线核验）+ 轻组织者后台，无人同时做透。
- **下一步**：确认 10 项开放问题（漏签退兜底、电子围栏半径、学号校验数据源、证书公章权威等），锁定试点校后启动 V1.0。

## 0. 角色与使用范围（v1.2 新增）

> 产品定位：**大学校园内的封闭志愿生态**。v1 阶段仅面向本校在校学生与校内志愿招募人员使用，不面向社会公众或校外机构。

### 0.1 使用范围

- **使用边界**：**志愿者参与者限本校在校学生**；**发布者可为校内人员（学生干部/社团/青协/教职工）或校外人员/机构（社区/公益组织/企业）**。v1 不面向社会公众（志愿者）开放。
- **招募约束**：所有志愿招募必须同时满足两点——①**招募对象（报名人员）为本校学生**；②**招募为"被本校认可、可增加志愿时长"的活动**（无论校内或校外发布者，均需经本校认可）。
- **数据隔离**：v1 单校部署 / 单校数据隔离，暂不做跨校互通（跨校/全国互通为后续版本目标）。

### 0.2 角色模型（双角色 + 校方管理员）

| 角色 | 身份要求 | 核心功能 |
|------|---------|---------|
| **学生（志愿者/参与者）** | 本校在校学生（学号 + 学校绑定校验） | 浏览/筛选活动、报名/候补/撤销、签到/签退、查看时长明细、导出证书、时长申诉 |
| **发布者（招募人员/组织者）** | 校内人员（学生干部/社团/青协/教职工）或校外人员/机构（社区/公益组织/企业），需身份/机构认证 + 发布权限开通 | 发布活动、分级编辑、取消活动、管理报名名单、批量时长/证书、导出上报、查看审计 |
| **校方管理员（P1+）** | 团委/学工/教务老师 | 校内认可/审核所有招募、时长认定、证书落款、审批、审计检索、数据看板、争议裁决 |

### 0.3 角色功能清单（学生端 / 发布者端 / 校方端）

**学生端功能（对应需求 R1-R7、R9、R13-R14、R34 等）**：
- 活动浏览与筛选（R1）、报名与学籍档案（R2）、本校学生身份校验（R3/R34）、签到签退（R4/R5）、时长统计与明细（R6）、证书导出（R7）、时长申诉（R9）、报名撤销/候补（R13）、时长溯源（R14）

**发布者端功能（对应需求 R21-R33、R11、R35-R36 等）**：
- 发布者身份/机构认证（R35）、招募认可申请（R36）、发布志愿招募（R21）、草稿箱（R22）、模板复用（R23）、发布后编辑（R24）、变更通知（R25）、活动取消（R26）、活动状态机（R27）、编辑权限分层（R28）、开始后锁定（R29）、防超卖（R30）、审计日志（R31）、预览（R32）、预填提示（R33）、名单导出/批量时长证书（R11）

**校方管理员端功能（P1+）**：
- 招募认可/审核（R36）、审批（R29）、审计检索（R31）、数据看板（R19）、争议裁决（R9）

### 0.4 身份与边界约束（"招募本校学生 + 本校认可可加时长"的落地）

- **学生身份**：注册/完善档案时必须完成「学号 + 学校」双重校验（R3 强化），未通过者不可报名。
- **发布者身份**：发布者可为**校内人员**（学生干部/社团/青协/教职工，本校身份认证）或**校外人员/机构**（社区/公益组织/企业，机构资质认证）；二者均需开通发布权限后方可发布。
- **报名门槛**：所有招募的招募对象（报名人员）必须为本校学生，活动发布时默认「仅限本校学生报名」。
- **招募认可（核心约束，统一机制）**：所有发布的招募（校内 + 校外发布者）均需经本校认可，方可标记为"可加时长"并进入学生报名池；**认可条件统一为「校内认可」**（由本校校方审核确认），不区分校内/校外的审核分级。
- **时长认定权归属**：所有志愿时长（含校外活动产生的时长）的最终认定/盖章权**统一归本校**；校外机构仅作为活动执行方，不持有时长认定权。
- **证书落款规则**：校内活动证书由本校单方落款；校外活动证书采用「**本校认可 + 校外机构联署**」落款（如"XX大学（认可）/ XX公益组织（承办）"）。
- **防冒用**：学号真实性校验（R3）+ 发布者权限分层（R28）+ 招募认可机制（R36）共同兜底，防止冒用身份或未认可招募混入。

## 1. 产品目标（3 个正交目标）

| # | 目标 | 一句话定义 | 对应北极星/关键指标 |
|---|------|-----------|--------------------|
| G1 | 30 秒打通「报名→签到→时长→证明」闭环 | 学生能以最低操作成本完成一次志愿活动的完整认证链路 | 签到完成率 ≥80%、激活率（注册 7 天内首笔签到认证）≥30% |
| G2 | 时长可信可溯源，防作弊达标 | 每一笔认证时长都能回溯到「活动→报名→签到→时长→认定」完整证据链，代签/漏记可被拦截与追责 | 签到埋点 method/gps_accuracy/distance_m/duration_credited；异常签到率显著低于行业水平 |
| G3 | 规范证明一键自动化，形成官方平台「上游入口」 | 单次与累计证明可自动化生成、编号可在线核验，组织者数据可一键导出对接官方平台 | 证书导出数、D7 留存 ≥25%、人均月认证时长 ≥2 小时 |

**目标关系**：G1 是体验底座，G2 是信任壁垒，G3 是价值放大。三者不可相互替代，共同支撑北极星指标「月活跃认证时长（Monthly Verified Volunteer Hours）」。

## 2. 用户故事（含验收导向）

### US-1 综测季冲刺导证书（画像 A：综测刷分党）
> 大二学生小李综测材料提交前夜，需要"累计总时长证明"和某次活动的"单次证明"。
- **验收导向**：Given 小李本学期已有 3 笔"已认定"时长；When 进入"我的时长"点击"导出累计证明"；Then 10 秒内生成含唯一编号+核验二维码的 PDF，且系统同步生成单次证明，无需二次填写任何字段。

### US-2 通勤路上 30 秒报名（画像 A）
> 小李在地铁上刷到活动，需立即占名额。
- **验收导向**：Given 小李已完善学籍档案；When 进入活动详情点击"报名"；Then 无需重复填写电话/学号/学院/班级（自动带出），30 秒内完成报名并进入报名记录，且名额满时提示"候补"而非静默失败。

### US-3 现场 GPS+二维码签到签退（画像 A/B，组织者 C 供给）
> 活动开始与结束，学生到场签到、离场签退，组织者防代签。
- **验收导向**：Given 活动已开启签到时间窗；When 学生在电子围栏内打开 GPS 签到；Then 签到成功并记录 gps_accuracy/distance_m；若 GPS 室内漂移失败，可回退现场动态二维码签到。签退同理，系统以"签退时间−签到时间"记实际时长。组织者视角，截图/过期二维码（>60 秒）均校验失败。

### US-4 组织者办活动全流程（画像 C：学生干部）
> 青协干部小张要发布活动、招募、现场签到、上报时长。
- **验收导向**：Given 小张用模板发布活动（名称/地点/时间/组织/岗位）；When 活动结束；Then 可一键导出 Excel/CSV 名单、批量录入时长、批量生成证书，且导出格式可对接志愿汇/中国志愿服务网。

### US-5 时长争议申诉（画像 A/B，组织者 C）
> 小李发现某次活动时长漏记/认定状态有误。
- **验收导向**：Given 小李在"时长明细"查看某条"待认定"记录；When 点击"申诉"提交理由与凭证；Then 进入组织者核对队列，状态流转可追踪，处理结果通过消息通知回传。

## 3. 用户研究洞察（来自瑞思）

### 3.1 三大画像

| 画像 | 规模/频次 | 核心诉求 | 关键痛点 |
|------|----------|---------|---------|
| A 综测刷分党 | 最大规模、最高频 | 最低成本攒够时长满足综测/评优/保研/入党门槛 | 抢不到名额、时长认定慢/漏记、不确定哪些活动算数、证书格式乱 |
| B 志愿达人/公益热心者 | 高忠诚、高传播 | 活动质量、个人公益档案、成就感反馈 | 缺长期成长档案与荣誉沉淀 |
| C 组织者/学生干部 | 关键供给方 | 高效发布/招募/签到/时长/向上交差 | 报名信息乱、签到防代签难、时长导出/证书批量生成/上报工作量大 |

### 3.2 痛点 TOP5（按影响度排序）

1. **时长认定不透明、易漏记**（影响度最高）——需"已认定/待认定"区分 + 全程溯源。
2. **签到体验差且防作弊难**——GPS 室内不准、二维码截图代扫。
3. **名额竞争与信息不透明**——需候补/撤销机制。
4. **证书生成不统一、不可验证**——需唯一编号 + 在线核验。
5. **报名信息重复填写、易错**——需学籍字段自动带出 + 学号真实性校验。

### 3.3 关键功能期望（直接转化为需求）

GPS 电子围栏 + 定位失败兜底（二维码/现场核销码）；动态二维码 30-60 秒防截图；签到+签退双端记录实际时长；时长可溯源（活动→报名→签到→时长→认定状态）；证书含唯一编号+二维码在线核验，支持单次与累计两种；学号真实性校验防冒用；报名可撤销/候补；组织者模板化发布 + Excel/CSV 导出 + 批量时长/证书 + 对接官方平台格式。

## 5. 数据依据（来自数析）

- **市场规模**：中国在校大学生约 4600 万，志愿服务参与率 65-75%，年度参与约 3000 万，高频核心约 2000 万；人均认证时长 20-30 小时/年；B2B2C 模式下 SaaS TAM 约 0.9-3 亿/年，整体 2-5 亿/年。
- **北极星指标**：月活跃认证时长（Monthly Verified Volunteer Hours）＝当月完成签到核验并计入档案的志愿时长总和。
- **关键指标**：激活率（注册 7 天内首笔签到认证）≥30%、签到完成率 ≥80%、D7 ≥25%、证书导出数、人均月认证时长 ≥2 小时。
- **分阶段目标**：
  - 0-3 个月：5-10 所试点校、1-3 万用户、激活 ≥30%、签到完成率 ≥80%。
  - 3-6 个月：30-80 校、10-30 万用户、月认证时长 ≥20 万小时。
  - 6-12 个月：200-500 校、100-300 万用户、月认证时长 ≥150 万小时。
- **埋点（P0 必须）**：user_register / activity_view / activity_signup / activity_checkin / certificate_export / hours_summary_view；checkin 事件带 method(gps/qr)、gps_accuracy、distance_m、duration_credited 等参数。

## 6. 需求池（P0 / P1 / P2）

## 7. 关键流程图（4 条核心流程）

### 流程 1：报名流程
```
学生进入活动列表
   → 筛选/搜索（R1）
   → 点击活动详情（查看名称/地点/时间/组织/岗位）
   → 点击"报名"
   → 判断：名额是否已满？
        ├─ 未满 → 校验学籍档案（R3）→ 自动带出电话/学号/学院/班级（R2）
        │          → 提交报名 → 写入报名记录 → 成功反馈
        └─ 已满 → 是否开放候补？
                    ├─ 是 → 进入候补队列（R13）
                    └─ 否 → 提示"名额已满"
```

### 流程 2：签到 + 签退流程
```
活动开始（组织者开启签到时间窗）
   → 学生到场 → 选择签到方式
        ├─ GPS 定位签到：判断是否在电子围栏内（distance_m 阈值）？
        │      ├─ 是 → 签到成功，记录 gps_accuracy/distance_m
        │      └─ 否/漂移 → 回退二维码签到
        └─ 二维码签到：扫描现场动态二维码（30-60s 刷新，R8）
               → 校验时效/防截图 → 成功/失败
   → 活动结束（开启签退）
   → 学生离场签退（同签到方式）
   → 系统计算 duration_credited = 签退时间 − 签到时间（R5）
```

### 流程 3：时长认定流程
```
签退完成 → 生成"待认定"时长记录
   → 组织者在后台核对（R9/R11）
        ├─ 通过 → 状态置为"已认定" → 计入总时长（R6）
        │          → 触发认定结果通知（R12）
        └─ 存疑 → 发起核对/退回
   → 学生可查看溯源链：活动 → 报名 → 签到 → 时长 → 认定状态（R14）
   → 学生可申诉/申请补录（R9）→ 组织者复核 → 状态更新
```

### 流程 4：证书导出流程
```
学生进入"我的时长"
   → 选择证书类型：
        ├─ 单次活动证明 → 指定某条"已认定"记录
        └─ 累计总时长证明 → 汇总全部"已认定"时长
   → 系统生成唯一编号 + 核验二维码（R7）
   → 渲染 PDF（含公章位/编号/明细）
   → 导出下载 → 埋点 certificate_export
   → 第三方扫码/输入编号 → 在线核验真伪（R10）
```

## 8. Non-goals（明确不做什么）

1. **不做全国/省市官方认证体系的替代**——不自建信用背书，定位为"校园执行工具 + 官方平台上游数据生产方"，认证权威仍归官方平台。
2. **v1 不做学分/综测的直接结算与发放**——只做规则展示（R17），不介入学校教务系统学分的实际认定与写入。
3. **不做即时通讯/社交社区**——不内置活动讨论群、私信聊天，社交激励仅限徽章/排行榜（R20，P2 且非 IM）。
4. **不做支付/资金募集/公益众筹**——产品不含任何资金流转功能，公益众包类资金场景不在范围。
5. **不做考勤硬件（人脸/闸机/NFC）的硬件研发与集成**——签到以手机 GPS + 二维码为界，人脸识别等硬件方案不纳入。
6. **不做跨平台原生三端同发**——v1 仅 Web + 微信/小程序或轻量 App 单端优先，iOS/Android 双原生不做。
7. **不做通用问卷/表单工具**——报名之外的通用数据采集（问卷星类场景）不在范围。
8. **不做面向社会公众（志愿者）的开放注册与跨校互通**——v1 志愿者仅限本校学生，跨校互通为后续版本目标；校外发布者（机构）可入驻，但其招募仍需本校认可、招募对象限本校学生。

### 9.4 排期建议与资源提示

**团队规模假设**：核心 1产品+3前端+2后端+1测试=7人（开发5人）；UI设计（Q1集中后转迭代）、校园运营（试点BD/地推，不计研发工时）兼职/外部。

**产能与折算**：理论 5开发×20人日/月≈100人日/月，按70%有效≈70人日/月。P0：46×1.3=60人日÷5开发=12人日/人≈2.4周纯开发，叠加设计/联调/试点筹备→日历6–8周。全量 P0+P1+P2=163人日（折算后），5开发并行约3–4个月纯开发，自然摊到Q1–Q3。

**关键路径与依赖**：
1. R3学号校验先于R2报名（报名带出真实档案，需先具备校验能力，且R3依赖试点校教务对接，最早启动）
2. R1活动展示先于R2报名
3. R4/R5签到签退 → R6时长统计 → R7证书导出（数据链路不可逆）
4. R7需预留R10在线验证（核验二维码规范V1.0就定义，避免Q2返工）
5. R8防作弊依赖R4/R5
6. R9申诉补录依赖R6+R14溯源
7. R11组织者后台是B端基础，R19看板依赖R11
8. R15官方格式导出依赖R6+R14溯源认定状态

**风险与缓解**：
- 学号校验对接缓慢→Q1最早启动，锁1–2所种子校先行，人工核验兜底
- 官方格式(R15)接口不明→Q1内冻结导出字段
- GPS精度不足→GPS+二维码+时间窗三重因子降级，室内二维码主判
- 防作弊vs「自愿好用」冲突→静默无感、只告警不强打扰
- 百万级并发→Q4前压测，R11/R19数据侧提前分库/缓存
- Q2峰值(68人日)→拆两段发布，R11独立小分队或前端临时+1
- R18/R20 ROI不确定→灰度小范围验证达标再全量
