                    1 问题定义

1.1 项目背景与意义

   志愿服务是高校立德树人的重要载体。近年来国家持续推动志愿服务制度化、
常态化，全国实名注册志愿者规模已达 2.4 亿人，志愿服务队伍 135 万支，累
计服务时长超过 53 亿小时。与此同时，大学生群体中“综测加分、志愿时长认
定”已成为普遍而真实的需求：调研显示，89.34% 的学生期望获得规范的志愿时
长认证，86.07% 的学生期望志愿时长能用于综合素质测评。然而与庞大需求形
成反差的是，校园志愿时长的记录与认定仍普遍依赖纸质登记、微信群接龙和
Excel 汇总，流程慢、易漏记、难核验。
   我们在调研中归纳出大学生志愿时长管理的三大痛点：第一，时长认定不透
明、易漏记，学生不清楚哪些活动“算数”，认定周期长且常常遗漏；第二，签到
防作弊难，室内 GPS 漂移、二维码截图代签现象屡见不鲜；第三，证书不可验
证，校外机构证书格式杂乱、没有唯一编号，真伪无从查证。基于以上背景，我
们小组选定“志愿时长认证与活动管理平台（青禾志愿）”作为本次软件工程课程
的项目主题。下面用 NABD 模型说明本项目的立项理由。

1.1.1 N（Need，需求）——解决用户的什么痛点

   核心需求可以概括为一句话：让每一份志愿付出都能被快速、真实、可验证
地记录。具体而言包括三点：一是学生希望“30 秒”内完成报名并全程掌握自己
的时长明细；二是组织者希望高效地发布招募、现场核销、批量登记时长并向上
汇总；三是校方希望所有招募经过本校认可、时长由本校最终认定，并能追溯审
计。这三点共同指向“报名—签到—时长—证明”的认证闭环。

1.1.2 A（Approach，做法）、B（Benefit，好处）、C（Competitors，竞争）与
D（Delivery，推广）

   A（做法）：我们采用“三端双角色 + 统一认可”的方案，构建学生端、发布
者端、校方端三套界面，以“学籍打通 + GPS 与动态二维码双签到 + 时长证据
链 + 唯一编号证书 + 组织者后台”作为差异化组合拳。

  B（好处）：学生可在 30 秒内完成报名并一键导出可核验证书；组织者从
招募到上报全流程线上化，减少大量重复录入；校方获得全校志愿数据看板与不
可篡改的审计日志，管理成本显著下降。
  C（竞争）：市面上志愿汇界面陈旧且未打通学籍；到梦空间存在代签风险；
省市级平台地域割裂、数据不互通；校园青协自建表格没有标准证书。尚无产品
同时做透“学籍 + 双签到 + 总时长档案 + 一键证书 + 组织后台”。
  D（推广）：以“种子校”策略优先落地一所高校，依托校团委/学工处官方背
书推广；再以“认可证书”作为价值锚点，逐步向周边院校与公益机构扩展。

1.2 项目基本目标

  本项目定位为“校园志愿执行工具 + 官方平台的上游数据生产方”，不做官
方认证的替代者。总体目标是用 30 秒打通“报名 → 签到 → 时长 → 证明”的
认证闭环，并以“月活跃认证时长”作为北极星指标。围绕该目标，我们设定三个
正交的子目标：
  ● 体验目标：学生报名 ≤ 30 秒，签退后即时生成时长记录，证书一键导出；

  ● 信任目标：双签到防代签、时长可溯源、证书唯一编号可在线核验、审计
  日志不可篡改；

  ● 价值目标：形成学生个人公益档案，为综测、评优提供可信数据支撑，并
  沉淀为校方可复用的数据资产。

1.3 可行性分析

1.3.1 技术可行性

  系统采用 Python 3 + Flask 构建后端，MySQL 8.0 作为主存储，配合 flask-
cors 解决跨域、PyJWT 实现无状态鉴权；前端为原生 HTML/CSS/JavaScript 高
保真原型，无需额外构建工具。数据访问层做了双引擎适配，在无 MySQL 环境
下可一键切换 SQLite 兜底运行。所用技术均为团队已掌握的成熟栈，实现风险
低，技术上完全可行。

1.3.2 经济可行性

  开发、部署所用软件均为开源免费（Python、Flask、MySQL、Gitee），前端
原型可直接由后端静态托管，无需购买服务器即可本地演示；因此项目几乎无额
外经济成本，经济上可行。

1.3.3 操作可行性

  三端界面沿用“青禾志愿”蓝紫品牌色与手机 App 式交互，符合大学生使用
习惯；报名、签到、导出证书等核心操作均在三步以内完成。组织者与校方角色
提供批量化、看板化工具，降低学习成本，操作上可行。

1.3.4 法律与合规可行性

  系统仅采集必要的手机号、学号与签到位置信息，密码使用 werkzeug 加盐
哈希存储，JWT 令牌鉴权，符合最小必要原则；数据本地存储、不对外泄露，合
规风险可控。

3.1 系统结构

   系统采用“模块化单体 → 微服务”的演进路线：现阶段以单个 Flask 应用承
载全部业务模块，按领域划分为认证、活动、报名、签到、时长、证书、申诉七
大模块，模块之间通过清晰的接口协作；未来可按需拆分为独立服务。系统分层
架构如图 3-1 所示。




                  图 3-1 系统分层架构图

   从下至上分为存储层、数据访问层、业务层、接入层与表现层：表现层为三
端 Web 原型；接入层负责路由、跨域与鉴权；业务层实现七大领域模块；数据
访问层统一封装 CRUD 并适配 MySQL/SQLite 双引擎；存储层保存七张核心
业务表。

3.4 关键算法设计

    系统最关键的两个算法是“签到幂等控制”与“签退自动生成时长”。签到时，
先校验用户是否报名该活动、是否已签到，再 INSERT 一条 checkin 记录；依
托 (activity_id, user_id, type) 唯一索引，即使并发重复提交也会被数据库拒绝，
返 回 “ 已 签 到 ， 请 勿重 复 签 到 ” 。 签 退 成功 后 调 用 _ensure_hours 生 成 一 条
status=pending 的时长记录，该函数先查重再插入，保证幂等；校方认定后才将
状态置为 verified，方可生成证书。流程如图 3-4 所示。

A.2 JWT 鉴权（后端 ·auth.py）

【后端 ·Python ·auth.py】
  def create_token(user_id, role):
      now = datetime.datetime.now(datetime.timezone.utc)
      payload = {'sub': str(user_id), 'role': role,
                'iat': now,
                'exp': now + datetime.timedelta(minutes=config.JWT_EXPIRE_MINUTES)}
      return jwt.encode(payload, config.JWT_SECRET, algorithm=config.JWT_ALGORITHM)

  def token_required(fn):
      @functools.wraps(fn)
      def wrapper(*args, **kwargs):
          auth = request.headers.get('Authorization', '')
          if not auth.startswith('Bearer '):
              return jsonify({'code': 40101, 'message': '缺少认证令牌'}), 401
          payload = decode_token(auth[7:].strip())
          request.user = {'id': int(payload['sub']), 'role': payload['role']}
          return fn(*args, **kwargs)
      return wrapper
说明：无状态鉴权：登录签发令牌，受保护接口用装饰器统一校验并把用户注入 request.user。

    if (p === '/') p = '/index.html';
    const fp = path.join(root, p);
    fs.readFile(fp, (err, data) => {
      if (err) { res.writeHead(404); res.end('not found'); return; }
      res.writeHead(200, {'Content-Type': types[path.extname(fp)]});
