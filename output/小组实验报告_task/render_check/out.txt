1.1 项目背景与意义

1.1.1 项目背景

  志愿服务时长是高校学生综合素质测评、评奖评优、推免资格的重要参考依
据。当前绝大多数高校的志愿活动管理仍停留在“群里接龙报名、纸质表格签到、
班委人工统计时长、截图充当证明”的原始阶段。这一流程存在四个突出问题：
一是报名信息分散在聊天记录中，学生事后翻找困难；二是签到依赖人工点名，
容易出现漏签、错签甚至“代签”“刷时长”等造假行为；三是时长由组织者手工汇
总，工作量大且容易出错；四是证书多为图片或简单文档，缺乏唯一标识与防伪
手段，校方在审核综测材料时难以辨别真伪。针对上述痛点，我们小组设计并开
发了“青禾志愿”志愿时长认证与活动管理平台，用一套可信、可追溯、可审计的
数字化流程替代传统的纸质流程。

1.1.2 调查访谈

  为准确界定用户需求，我们访谈了三类典型用户，形成了清晰的用户画像与
痛点清单。
  （1）普通学生：大二学生小林每学期参加 3~5 次志愿活动，综测前需要反
复翻聊天记录找报名截图、自己用计算器累加时长，并且担心“自己算的时长不
被认可”。他最希望“时长自动、透明、可导出正式证明”。
  （2）班级组织委员：班委小周每次组织活动都要手工建 Excel 统计名单、
现场拿纸质表点名核销、结束后再手动登记时长并上报，一次 30 人的活动要花
费半天时间，还常因漏登被同学投诉。她最需要“批量报名、现场快速核销、一
键导出上报”。
  （3）校团委/志愿组织负责人：指导老师最头疼的是“时长认定缺少依据、证
书真伪难辨、历年数据分散无法审计”。他需要“可追溯的签到凭据、统一编号可
核验的证书、以及全校层面的数据看板”。
  访谈结论：三类用户共同指向一个核心诉求——把“报名、签到、时长、证

1.1.4 项目意义

  对学生而言，平台提供透明可查的时长明细与一键导出的正式证明，省时省
心且更有公信力；对组织者而言，批量报名、现场核销、批量登记与导出上报显
著降低组织成本；对校方而言，签到凭据可追溯、证书唯一可核验、数据集中可
审计，从根本上堵住了时长造假的漏洞，为志愿服务评价提供了可信的数据底座。

1.3 可行性分析

1.3.1 技术可行性

  系统采用 Python + Flask 作为后端框架，MySQL 8.0 作为主数据库、SQLite
作为无环境兜底，前端使用原生 HTML/CSS/JavaScript 实现三端高保真原型。这
些均为成熟、文档完善、社区活跃的开源技术，且团队成员在课程前已具备 Web
开发与数据库基础。核心难点——签到防作弊与时长防重复，可通过数据库唯一
索引与业务幂等设计解决，技术风险可控。

1.3.2 经济可行性

  本项目全部采用开源技术栈，无任何软件授权费用；开发与运行仅需一台普
通服务器或云主机（最低配置即可），数据库与代码托管于 Gitee 平台免费完成。
相较于采购商业志愿服务系统或继续投入大量人工，本方案几乎零成本，经济上
完全可行。

1.3.3 社会与操作可行性

  项目顺应高校志愿服务数字化、规范化的趋势，符合校团委对“时长可信、
可审计”的管理诉求，也契合学生对“便捷、透明、有证明”的期待，具备良好的社
会接受度。操作上，系统面向手机浏览器使用，无需安装客户端，交互流程贴合
学生既有习惯，组织者与校方仅需经过简单培训即可上手，推广门槛低。

2.1 需求分析概述

2.1.1 NABCD 模型分析

   我们运用 NABCD 模型对项目立项理由进行了系统分析，明确项目的需求、
做法、收益、竞争与推广策略。
   N（Need，需求）：志愿服务时长是综测、评优的硬指标，但现有流程低效、
易出错、易造假，学生、组织者、校方三方都缺少一个可信、便捷的统一平台。
这是最根本的用户痛点，也是本项目的原始出发点。
   A（Approach，做法）：构建三端协同的 Web 平台——学生端负责报名与
查证，发布者端负责招募与核销，校方端负责认定与审计。技术上以“GPS + 动
态二维码双签到”防代签、以数据库唯一约束保证时长幂等、以“唯一编号 + 二
维码”实现证书在线核验，从流程和技术双重层面建立信任。
   B（Benefit，收益）：学生获得透明时长与可信证明，省去翻记录、算时长
的烦恼；组织者告别手工统计，效率大幅提升；校方获得可追溯、可审计、防造
假的数据底座，志愿服务评价更公正。
   C（Competitors，竞争）：如 1.1.3 节竞品分析所述，志愿汇、i 志愿等通用
平台在校园精细化场景覆盖不足，传统人工流程则完全无法保证可信度。我们以
“校园可信时长认证”这一差异化定位切入，避开正面竞争。
   D（Delivery，推广）：通过校内志愿社团、班级组织委员渠道在校园内推广，
发布 Gitee Page 介绍页供同学试用，并争取校团委支持将系统纳入志愿服务认
定流程，形成口碑传播。

2.1.3 功能创新

   本项目的核心创新在于“可信时长认证闭环”，这也是评分维度中“功能创新
（10%）”的着力点。与常见报名工具相比，我们重点解决“时长是否真实、证书
是否可信”这一关键问题，具体体现在四处信任壁垒：

• 双签到防作弊——签到同时校验 GPS 位置与动态二维码，签退再次校验，杜
绝“代签”“只签到不干活”。

• 时长可溯源——每次时长记录都关联活动、报名、签到记录，校方认定时可追
溯完整凭据链。

• 证书唯一可核验——每张证书分配“QH-年份-随机码”唯一编号与唯一二维码
令牌，任何人扫码即可在线核验真伪，杜绝 PS 造假。

• 审计不可篡改——关键操作记录操作者与时间，形成审计日志，为校方提供可
审计依据。

3.4 关键算法设计

3.4.1 签到签退与时长幂等算法

  签到/签退是系统最核心、也最易出错的环节。核心难点在于：如何在网络重
试、并发点击等情况下，保证“一次活动只产生一条签到、一条签退、一条时长
记录”，避免时长被重复累加。算法流程如图 3-5 所示。




           图 3-5   签到签退与时长生成算法流程


                           21
     华 中 科 技 大 学 计 算 机 科 学 与 技 术 学 院 软 工 项 目 报 告

   算法的关键设计如下：（1）签到时先校验该用户是否已报名，未报名则拒
绝；（2）写入 checkins 表时，依赖 (activity_id, user_id, type) 唯一索引兜底，
重复签到会触发唯一约束冲突而返回“已签到”；（3）签退时同样校验并写入唯
一记录，随后调用 _ensure_hours 生成时长；（4）_ensure_hours 先查询该活动
该用户是否已有时长记录，已有则直接跳过，从业务层再次保证幂等。通过“数
据库唯一约束 + 业务查重”双重保险，彻底杜绝重复累加。

3.4.2 时长认定算法

   签 退 生 成 的 时 长 初 始 状 态 为 pending （ 待 认 定 ） ， 校 方 管 理 员 通 过
hours_verify 接口将其置为 verified（已认定）并记录认定人与认定时间，或通过
hours_reject 接口驳回。只有状态为 verified 的时长才能用于生成证书，从而保
证证书所载时长均经过校方认可，具备公信力。

3.4.3 证书编号与核验算法

   证书编号采用“QH-年份-8 位随机大写十六进制”的格式生成，如 QH-2026-
3A7F9C2D，并同时生成唯一的二维码令牌。生成证书前校验时长状态必须为
verified ， 否 则 拒 绝 。 核 验 时 ， 任 何 人 通 过 证 书 编 号 或 二 维 码 调 用 公 开 的
/api/v1/verify 接口，即可查询到证书持有者、时长、落款单位等信息，实现“扫码
即验真”。

3.5 数据管理说明

   系统涉及的数据统一采用关系型数据库存储与访问。主数据库选用 MySQL
8.0，字符集 utf8mb4、存储引擎 InnoDB，共 7 张表，通过外键与唯一索引保证
数据完整性。同时，为便于零环境快速演示，数据访问层 db.py 实现了 MySQL
与 SQLite 双引擎适配：通过配置项 DB_ENGINE 切换，自动处理 SQL 占位
符（? 与 %s）与 Decimal 类型的差异，上层业务代码无需感知底层数据库，做
到“一处配置、双引擎可用”。

4.2.2 签到签退模块

   def create_token(user_id, role):
       now = datetime.datetime.now(datetime.timezone.utc)
       payload = {'sub': str(user_id), 'role': role, 'iat': now,
                 'exp': now + datetime.timedelta(minutes=config.JWT_EXPIRE_MINUTES)}
       return jwt.encode(payload, config.JWT_SECRET, algorithm=config.JWT_ALGORITHM)

   def token_required(fn):
       @functools.wraps(fn)
       def wrapper(*args, **kwargs):
           auth = request.headers.get('Authorization', '')
           if not auth.startswith('Bearer '):
               return jsonify({'code': 40101, 'message': '缺少认证令牌'}), 401
           payload = decode_token(auth[7:].strip())
           request.user = {'id': int(payload['sub']), 'role': payload['role']}
           return fn(*args, **kwargs)
       return wrapper

A.6 数据访问层（后端 ·db.py）

  def get_conn():
      return _mysql_conn() if config.DB_ENGINE == 'mysql' else _sqlite_conn()

  def _translate(sql):
      return sql.replace('?', '%s') if config.DB_ENGINE == 'mysql' else sql

  def query(sql, args=()):
      conn = get_conn()
      try:
          cur = conn.cursor()
          cur.execute(_translate(sql), args)
          return _rows_to_dicts(cur.fetchall())
      finally:
          conn.close()
如何运行：统一 CRUD 封装，屏蔽 MySQL/SQLite 差异（占位符与 Decimal 类型转换），

  require('path');
  const PORT = process.env.PORT || 8787;
  http.createServer((req, res) => {
    let p = decodeURIComponent(req.url.split('?')[0]);
    if (p === '/') p = '/index.html';
    const fp = path.join(root, p);
    fs.readFile(fp, (err, data) => {
      if (err) { res.writeHead(404); res.end('not found'); return; }
      res.writeHead(200, {'Content-Type': types[path.extname(fp)]});
      res.end(data);
    });
  }).listen(PORT, '127.0.0.1', () => console.log('serving http://127.0.0.1:'     +
  PORT));
